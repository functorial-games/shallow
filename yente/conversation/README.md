# Yenta conversational prototype

The executable accepts fictional conversation records, validates attributed interpretations and response plans, applies corrections, and controls exact approved retellings. It provides a reusable deterministic core around a language-model boundary. The included replies are explicitly assistant-authored recorded illustrations. Live inference and open-ended language understanding have not been established by those illustrations.

The source lives in `examples/autogenerated/yente-conversation/`. Its `Main.idric` imports the shared evidence, audience, challenge, conversation, disclosure, command, and journal modules. `materials/` holds the attributed source register, original challenge records, character policy, and dialogue examples.

## Executable interface

The entrypoint accepts these argument sequences. `STATE_ROOT` is a canonical absolute path to a trusted, writable scratch directory. `MATERIALS`, command files, request files, and response files should be supplied as absolute paths for reproducible execution.

```text
yente-conversation script STATE_ROOT MATERIALS COMMANDS
yente-conversation demo STATE_ROOT MATERIALS
yente-conversation request STATE_ROOT MATERIALS SESSION OUTPUT
yente-conversation accept STATE_ROOT MATERIALS SESSION REQUEST RESPONSE
```

`script` applies commands from a UTF-8 TSV file. `demo` accepts the same commands on standard input until `quit` or end of input. Explicit actor and session fields are fictional demonstration controls, not authentication.

`request` writes the permitted context, eligible moves, relevant attributed challenge records, and character policy for a model stage. `accept` verifies that the saved request still matches the current request, parses the supplied plan, validates it against the current context, persists it, and emits the response. A caller can use a recorded response through this interface. The interface itself does not call a live model or establish semantic understanding.

Successful mutations are saved before their output is emitted. Invalid commands emit an `ERR` record without changing the state; script processing may continue after such a record, so consumers must inspect command outcomes rather than treating process exit alone as acceptance. A storage failure terminates the process.

## Command records

Each record occupies one line. Fields are separated by literal tabs; the spaces in the following notation stand for field boundaries. Text fields accept unfamiliar text without a fixture-name or exact-sentence dispatch. Literal tabs, line breaks, CR and NUL are not allowed inside an ordinary text field. An empty event date means unknown; report time remains a separate field. Comma-separated identifier lists use `-` for an empty list.

| Operation and fields | Effect |
| --- | --- |
| `person PERSON` | Register a fictional person |
| `session SESSION ROLE SUBJECT PARTICIPANTS PURPOSE` | Create an immutable audience/session identity; role is `partner`, `parent`, `friend`, or `shared` |
| `consent SESSION TALK RETAIN` | Set explicit discussion and retention choices, each `yes` or `no` |
| `topic SESSION TOPIC` | Select a discussion topic |
| `prefer SESSION TEXT` | Record an explicit response preference |
| `defer SESSION TOPIC` / `resume SESSION TOPIC` | Defer or resume a subject |
| `say SESSION ACTOR KIND EVENT_TIME REPORT_TIME TEXT` | Add an attributed report, hearsay, wish, hypothetical, or report of an agreement |
| `hypothesis SESSION ID EVIDENCE_IDS DEPENDENCY_IDS TEXT` | Add a tentative, evidence-supported interpretation |
| `withdraw SESSION ACTOR HYPOTHESIS` | Withdraw an interpretation and its dependents |
| `correct SESSION ACTOR EVIDENCE KIND EVENT_TIME REPORT_TIME TEXT` | Supersede that speaker's own account and invalidate dependent interpretations and plans |
| `proposal SESSION ACTOR ID RECIPIENTS DESTINATIONS TEXT` | Draft an exact retelling from a solo source session |
| `edit ACTOR PROPOSAL REVISION RECIPIENTS DESTINATIONS TEXT` | Edit a pending retelling; prior approval becomes invalid |
| `approve ACTOR PROPOSAL REVISION TEXT` | Approve exact current wording and revision |
| `deliver ACTOR PROPOSAL REVISION REPORT_TIME` | Recheck permission and copy the approved statement to the named permitted sessions |
| `revoke ACTOR PROPOSAL` | Prevent further use, withdrawing copied context and its dependents without erasing historical delivery |
| `agreement SESSION ACTOR ID PARTICIPANTS TEXT` | Create a pending agreement |
| `agreement-edit ACTOR AGREEMENT REVISION TEXT` | Change the proposal and invalidate prior confirmations |
| `confirm ACTOR AGREEMENT REVISION TEXT` | Confirm only for the acting participant |
| `answer SESSION MOVE TARGET EVIDENCE_IDS DEPENDENCY_IDS CHALLENGE TEXT` | Validate and record a supplied response plan |
| `show SESSION` | Inspect that session's permitted context |

For transport retries, wrap a command in `event`, an explicit operation identifier, and the original command fields:

```text
event<TAB>story-001<TAB>say<TAB>lio-private<TAB>lio<TAB>wish<TAB><TAB>2026-01-10<TAB>I want Sunday lunch with my parents most weeks.
```

The notation `<TAB>` denotes one actual tab, not those five literal characters. Repeating the same event identifier and identical command returns its receipt without applying another transition. A previously spoken Yenta reply returns only `OK replayed EVENT_ID`, so a retry cannot emit old wording after a correction or revocation. Read operations cannot be wrapped as events. Reusing an identifier with different input is rejected. A new identifier represents a new event even if the words happen to be the same. Bare mutating commands remain supported but do not provide general transport retry identity. Event receipts do not enter the model context.

## Model request and response framing

The request begins with `YENTA_MODEL_REQUEST_V1`. Context rows consist of consecutive values encoded as decimal character count, colon, and value. Counts concern decoded characters, not UTF-8 byte lengths. Each row ends with a newline. Quoted utterances and policy/material values remain data inside their declared framing. The model is instructed to ignore instructions embedded in quoted accounts; deterministic validation still treats its response as an untrusted proposal.

A response is exactly one seven-field TSV row:

```text
plan<TAB>MOVE<TAB>TARGET_UNCERTAINTY<TAB>EVIDENCE_IDS<TAB>HYPOTHESIS_IDS<TAB>CHALLENGE_ID<TAB>WORDING
```

Moves are `episode`, `expectation`, `constraint`, `hypothetical`, `interpretation`, `revisit`, `summarize`, `disclosure`, and `pause`. References must belong to the current permitted session. A question requires current evidence. Challenge selection must match the session's audience and topic. Deferred or nonconsenting discussions permit summarizing or pausing. This validation establishes structural and permission rules, not whether arbitrary generated wording follows logically from an account.

## Family illustration

`fixtures/family.tsv` contains five invented people: prospective partners Lio and Mira; Lio's parent Nera; Mira's parent Daro; and Lio's friend Suri. Each private session contains that participant's own account. The shared couple session initially contains no private stories.

The script seeds an explicitly tentative interpretation of Lio's visiting wish, records an illustrative question, and then applies Lio's correction. The corrected evidence is `lio-private-e2`; the old interpretation and its dependent question are withdrawn. Both partners then approve exact retellings for the couple's session, and its shared question uses only those delivered statements. The final `show` commands permit inspection of the shared and corrected private contexts.

`fixtures/family-response.tsv` is one original assistant-authored recorded plan for the final `lio-private` session. It is suitable for the `request`/`accept` interface after the family script. Its wording was supplied as an illustration, not produced by live inference. The fixture also includes different original replies to Mira, each parent, and the friend, grounded only in their own session records. Running it exercises the same generic command and validation functions used for other names and accounts.

## Persistence and evidence limits

`Store.idric` writes a versioned UTF-8 journal under `STATE_ROOT`. It checks strict UTF-8 and complete framing, writes `journal.new`, checks write/flush/close, and uses same-directory atomic rename to replace `journal.tsv`. The prior committed journal survives a failed replacement. An orphan temporary file is ignored when a valid committed journal exists; a temporary journal without a committed journal fails closed for explicit recovery. Corruption and ordinary IO errors are not treated as an empty conversation.

An exclusive `.lock` directory makes overlapping storage calls fail closed. A crash may leave that lock requiring deliberate review and recovery. This is a synthetic single-process store with trusted directory ancestry, not a symlink-safe or multi-process read/modify/write transaction. Atomic replacement does not establish fsync or power-loss durability.

The demonstration does not implement production identity verification, encrypted private storage, confidential ingestion, training, or deployment. Source compilation, deterministic executable checks, recorded model-boundary replay, live model conversations, and independent acceptance must be reported as separate evidence. See `examples/autogenerated/yente-conversation/attempt.md` for the actual compiler and execution receipt. No merge or deployment follows from running this prototype.

Correction, revocation and interpretation withdrawal conservatively clear prior
Yenta wording in the affected session from future context. A model may have used
an input without declaring it in its citations; withdrawal therefore does not
rely solely on those declarations. Participant accounts and unrelated sessions
remain, and the original journal remains an audit. See
`acceptance/uncited-withdrawal/` for the actual pre-fix rejection and repaired
before/after request from the same fictional journal.

## Fresh model trial

`examples/autogenerated/yente-live-model/live_trial.pi` adds fresh inference
through the existing checked Ithon Transformers/Torch boundary. The Idriç core
still constructs each permitted request and admits each proposed plan. The
adapter receives that request only. It does not read the journal. Its strict
JSON-to-TSV codec refuses malformed model output and retains the raw failure;
there is no recorded-answer substitute or automatic repair.

The hosted workflow provisions Cat Food's model runtime on Ubuntu x86_64 and
uses pinned Qwen/Qwen2.5-1.5B-Instruct, revision
`989aa7980e4cf806f80c7fef2b1adb7bc71aa306`, in float32 on CPU. A positive
Linux/x86_64 and 12 GB physical-memory preflight precedes loading. The eight fictional
cases exercise a partner, the other partner, a parent, a friend, an answer, a
correction, a topic deferral, and a shared discussion containing only two exact
approved retellings. An unrelated private sentinel must never enter a prompt.
A separate first-turn comparison omits the detailed character policy while
retaining the same scoped data and output contract. It is a diagnostic sample,
not evidence of quality improvement.

The Flexible Pipes live pipeline retains the actual request, prompt, input and
output token IDs, raw output, model/runtime/source identities, codec decision,
core admission and failures. ai-ci's independent `Live.idric` reconstructs the
plan from the raw output, compares it with actual admission, and checks bounded
scope and deferral observations. Check-only and prepare-only execution do not
establish inference. This small model qualifies wiring and reveals behavior;
interpreting its wording and developing Yenta's voice require grounded review
of the actual hosted transcript.

The first completed trial and its real failures are retained in
`acceptance/first-live-refusal/`. The adapter now declares the syntax-only `{`
assistant prefill separately from the unmodified generated completion. The
observer reconstructs the complete JSON from those exact bytes; it does not
repair or replace a model answer. Bank metadata precedes the particular
account, with eligible moves last, so the request does not end on a canned
opening question.

## Fictional person model

Use the existing `script`, `demo`, `request` and `accept` entry points.
The first dimension designates a consenting solo session as that person's
intake. Each person has their own set of dimension IDs. An ID can be opaque.
The display name can be empty, and the tags can be empty. Register dimensions
as questions arise. There is no fixed questionnaire.

| TSV fields | Effect |
| --- | --- |
| `dimension SESSION AXIS NAME TAGS OPEN_QUESTION` | Introduce a dimension with an unresolved question and an entirely unbounded coordinate. |
| `ask-next SESSION` | Speak the first eligible open question that has not already been asked in its current wording. Discussion consent, deferred topics and tags apply. |
| `reply SESSION ACTOR QUESTION KIND EVENT_TIME REPORT_TIME EXACT_TEXT` | Retain the exact attributed answer, the ID of the question it answers and the last question the speaker had heard. Coordinates keep their previous uncertainty. |
| `thread SESSION` | Read the private historical questions in delivery order, with previous/next IDs and replies. Includes unanswered and withdrawn questions. |
| `note SESSION AXIS ID FIELD EVIDENCE_IDS DEPENDENCY_IDS LOW HIGH VALUE REMAINING_QUESTION` | Attach a named text field, a tentative reading, evidence pointers, an optional interval and the question that reading leaves open. Competing readings can coexist. |
| `review-source SESSION EVIDENCE_ID` | Reopen prior interpretations after a later account calls the source into question. Cite the actual reason. |
| `project SESSION AXIS=WEIGHT,...` | Compute a temporary, person-specific linear projection. Zero weight discards a dimension for this calculation. |
| `shareable SESSION RECIPIENT DESTINATION` | Return only exact, approved, pending wording eligible for that recipient at that destination. Existing delivery and revocation commands control actual sharing. An empty result withholds everything. |

`show` and model requests carry the current dimensions, tentative notes, source
review references and eligible lines of inquiry for the intake. `thread` is a
separate historical read. Use `reply` when the eliciting question is known.
An ordinary `say` or an older journal cannot establish that link retrospectively.
Use `correct` to supersede an attributed account and `withdraw` to retire a
reading. An event ID distinguishes a transport retry from intentional repetition.

The numeric layer represents a box of possible real coordinates. Bounds and
coefficients in this mock accept signed decimal integers. An asterisk denotes
an open end. The outer interval covers all active alternatives on an axis,
including conflicting ones. Cross-axis dependence is unknown, so a projection
can be wider than the true range. Reading and projecting never narrow a bound.
A keyed note can hold text and an unresolved question with both ends open.

A source review withdraws interpretations supported by the person's existing
intake answers, their transitive dependents, and prior model wording in the
affected intake. It records the reason beside the original accounts and closes
pending retellings. Newly entered readings of those accounts must cite the
review basis as well. The original words and earlier deliveries remain in
history. Another participant's private session never receives the reason.
Review is a supplied mock event. The model makes no diagnosis of deception.

The regression fixture and its expected transcript are
[`person-model.tsv`](fixtures/person-model.tsv) and
[`person-model.expected`](fixtures/person-model.expected). Run the fixture via
`script` with a fresh state directory and compare stdout byte-for-byte. It
contains deliberate refusals. The service transport can exercise the core via
these commands when a caller connects its dispatcher to the executable.
